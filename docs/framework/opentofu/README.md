# OpenTofu

Our modules are written in standard HCL against published providers, so they work with [OpenTofu](https://opentofu.org) as well as with Terraform. We run Terraform in our pipelines today; this page records what holds if a consumer - or we - switch.

## Compatibility

- [Building blocks](../terraform/BUILDING-BLOCKS.md) use only language features present in both: `optional()` object attributes, `try()`, `dynamic` blocks, `import` blocks and variable validation that references locals. The declared `required_version` is the Terraform floor; the equivalent OpenTofu floor is its matching release.
- Providers come from the public registry and resolve identically for both CLIs.
- Nothing in our modules depends on Terraform Cloud, and `backend "azurerm"` is supported by both.

## What to watch

- **Documentation is generated by `terraform-docs`** and refers to Terraform by name. That is cosmetic, but keep it consistent within a repository.
- **State is not a compatibility layer to experiment with.** A state file written by one CLI should be migrated deliberately, with a backup of the blob, never by pointing both CLIs at the same key.
- **Version constraints are the real risk**, not the CLI. Pin as described in [Root Modules](../terraform/ROOT-MODULES.md).

## Switching a workspace

The [workspace](../terraform/WORKSPACES.md) layer is where a switch happens: the pipeline template installs the CLI and runs `init`, `plan` and `apply`. Swapping the binary is a pipeline parameter change, and it is decided per workspace - never for a subset of a single state.

> _The layering is CLI independent; the state is not._
