# Root Modules

A **root module** composes [building blocks](./BUILDING-BLOCKS.md) into one deployable domain - the databases of the corporate estate, the governance hierarchy, the production runtime. It is the layer that knows *what* a domain consists of, but never *where* it is deployed or *with which values*; that belongs to a [workspace](./WORKSPACES.md).

Root modules live in `wanted-cloud/terraform-wanted-<domain>` and are consumed by exactly one workspace repository per environment.

## Repository layout

```
terraform-wanted-<domain>/
├── backend.tf              # empty backend block - configured by the pipeline
├── providers.tf            # provider configuration, including aliases
├── versions.tf             # terraform and provider version constraints
├── variables.tf            # the domain's input contract
├── main.tf                 # shared data sources, and the README header comment
├── <resource-family>.tf    # one file per family: resource-groups.tf, psql-databases.tf, ...
├── Makefile
├── README.md               # generated by terraform-docs
└── .terraform-docs.yaml
```

Files are named after what they create, in the plural - `resource-groups.tf`, `subscriptions.tf`, `mysql-group-roles.tf`. A reviewer should be able to guess the filename from the change request.

## Consuming building blocks

Building blocks are referenced by their Git source and pinned with a `ref`:

```hcl
module "resource_group" {
  for_each = { for rg in var.resource_groups : rg.name => rg }
  source   = "git::https://github.com/wanted-cloud/terraform-azure-resource-group.git?ref=main"

  name     = each.value.name
  location = each.value.location != "" ? each.value.location : null
  tags     = merge(each.value.tags, var.global_tags)
}
```

- **`for_each` over a list variable, keyed by name.** Adding an instance is a data change in the workspace, never a code change here.
- **`merge(each.value.tags, var.global_tags)`** so every resource in the domain carries the domain's tags.
- **Module labels are singular and snake_case** (`module "resource_group"`), resource families in variables are plural (`var.resource_groups`).

> **Pinning:** `?ref=main` means the estate follows the block's default branch. That is convenient while a block is young and dangerous once it is shared - a provider major release reaching an unpinned block has broken a whole estate before. Once a block is tagged, pin the tag (`?ref=0.1.0`) and bump it deliberately.

## Variables carry the shape, tfvars carry the values

Every deployable thing is a `list(object({...}))` with `optional()` defaults, so the workspace states only what differs from the default:

```hcl
variable "postgresql_servers" {
  description = "List of PostgreSQL Flexible Server instances to deploy."
  type = list(object({
    name                = string
    resource_group_name = string
    location            = string

    sku_name           = optional(string, "B_Standard_B1ms")
    postgresql_version = optional(string, "16")

    storage = optional(object({
      mb                = optional(number, 32768)
      auto_grow_enabled = optional(bool, false)
    }), {})
  }))
  default = []
}
```

Defaults encode the house standard; the workspace overrides only the exceptions. A `default = []` on every collection means a fresh workspace deploys nothing until it asks for something.

## Providers

`providers.tf` is the only place a provider is configured. Cross subscription work is done with **aliases**, never with a second root module:

```hcl
provider "azurerm" {
  features {}
}

provider "azurerm" {
  features {}
  alias           = "connectivity"
  subscription_id = var.connectivity_config.subscription_id
}
```

Subscription ids arrive as variables, so the same code serves production and any other estate.

## Backend

`backend.tf` declares the backend **type only**:

```hcl
terraform {
  backend "azurerm" {}
}
```

The rest - storage account, container, key, subscription, resource group - is partial configuration supplied at `terraform init` time by the pipeline. This is what allows one root module to back many workspaces, each with its own state. See [Workspaces](./WORKSPACES.md).

## Adopting existing resources

Infrastructure that predates the code is adopted with `import` blocks rather than recreated:

```hcl
import {
  for_each = { for mg in var.management_groups : mg.name => mg }
  id       = format("/providers/Microsoft.Management/managementGroups/%s", each.value.name)
  to       = module.management_group[each.key].azurerm_management_group.this
}
```

> **Never delete a live resource to resolve a conflict.** A `409` on apply means the object already exists and Terraform does not know about it - import it. Deleting to "let Terraform recreate it" destroys whatever depended on it.

## Documentation

`README.md` is generated by terraform-docs, and the root module configuration renders `{{ .Modules }}` as well, so the README lists every building block the domain consumes and at which ref. Run `make package` before committing.

## Rules

1. **No values in code.** No subscription id, object id, location or CIDR in a `.tf` file; all of it arrives through variables.
2. **No resource without a block.** If a building block exists, use it. If one does not exist and the resource is reusable, write the block first.
3. **One domain per root module.** If two halves of a repository never reference each other, they are two domains.
4. **Additive by data.** Deploying one more of anything must be a workspace change only.
5. **Plan is the review artefact.** The pipeline plans, a human approves, then it applies - never apply from a workstation.

> _A root module should read like an inventory, not like a program._
